# Prototype Instructions

Run the local server yourself and open the preview in the browser available to this environment. Do not give the user server-start instructions when you can run it.

Before making substantial visual changes, use the Product Design plugin's `get-context` skill when the visual source is unclear or no longer matches the current goal. When the user gives durable prototype-specific design feedback, preferences, or decisions, record them in `AGENTS.md`.

When implementing from a selected generated mock, treat that image as the source of truth for layout, component anatomy, density, spacing, color, typography, visible content, and hierarchy.

Build app UI in `src/`. Keep `.openai/hosting.json`, `worker/index.js`, `scripts/prepare-sites-build.mjs`, and `tests/sites-worker.test.mjs` intact so the same local prototype can be handed to Sites. Before a Sites handoff, run `npm run build` and `npm run test:sites`; the build must leave `dist/client/index.html`, `dist/server/index.js`, and `dist/.openai/hosting.json`.

## Product decisions

- Use a restrained Codex-style shell: a Space tree sidebar, a full-size Main Page surface, and a bottom Main Thread dock. The dock is collapsed by default, keeps the pending/latest message above the input, and expands into the full conversation without displacing the page. Do not expose JSON-RPC logs or manual executable-path controls in normal UI.
- Detect Codex automatically from PATH and show an actionable notice if it is missing.
- The browser and Tauri window share one local Rust service and the same Codex thread state. The installed service also serves the browser UI; it must work without a Vite development server.
- Keep Codex external to the installer to preserve the small package size. Persist project data under `.space/`.
- `../SPEC.md` is the product authority. Space and runnable View pages are the main experience; a chronological chat feed alone is not an acceptable implementation. Keep one Main Thread per project workspace and explicit ownership for each View Thread.
- Match the user's Codex desktop screenshots for the composer, unified model/effort/speed control and permissions. Use the supplied visual/source assets; do not invent replacement controls or add unrelated styling.
- Separate domain state, persistence, Codex protocol, orchestration and UI components. Persist layout and View versions directly through the Space service.
- Do not add synthetic window chrome, generic horizontal workspace/Space headers, canvas action bars, or undo/redo controls. The Main Page should start directly below the app shell; do not render a competing node canvas.
- Keep the primary sidebar focused on the Space tree only; do not add a local-workspace label, recent-chat list, or duplicate chat/search entry points.
- Keep Space creation discoverable without adding chrome: reveal a compact plus action on Space section hover/focus and open the directory picker from it.
- The Space directory picker supports creating a folder in the current location and then selecting it, with macOS-style navigation and keyboard shortcuts. Single click selects, double click enters; creation must report name conflicts or permission errors without overwriting anything. Keep these controls inside the picker, not in the main app shell.
- Keep the composer focused: show permission, file attachment, unified model/effort/speed control and send/stop. The project is already selected by the Space sidebar, so do not repeat a project-directory row inside the conversation. Do not expose a "此计算机" context chip or unreliable voice input control.
- The model, effort and speed triggers must share one popover. The popover uses a direct-manipulation effort track with pointer and keyboard support, model and speed subviews, outside-click/Escape dismissal, and short opacity/scale transitions.
- Sending while a Main or View Thread is running must remain available. Messages sent during an active turn enter a bounded, locally persisted queue and resume in order when the target thread becomes idle. Each queued row exposes four lightweight actions: guide explicitly steers the active turn (or moves it into the composer when idle), edit changes the queued text and clears a delivery error, delete removes it, and pointer dragging or keyboard movement reorders it. Ordinary send must never silently steer an active turn. The queue keeps the model, effort, speed and permission captured at send time so later control changes do not rewrite pending work.
- Brand the shell as Chat UI. Use the local vector `ChatUiLogo` mark; do not reuse the Codex terminal glyph or raster logo.
- Main Thread owns Space plans and the Main Page manifest. A plan creates or reuses View records and starts child View Threads. A View Thread owns only its assigned page and publishes structured HTML/status back to its own View; never let a child rewrite the main page composition or another View.
- Main Thread plans are authoritative composition snapshots: connections are replaced on every accepted plan, while View deletion must use explicit `removeViews` IDs so a partial response cannot erase omitted work. Matching an id-less retry by View title is allowed to prevent duplicate surfaces.
- Switching between a project's Main Thread and View Threads updates both the page iframe and its owned conversation. The expanded dock must show the full saved dialogue and public execution steps, including live replies and accumulated command/tool output. Preserve these after completion and reload; never mix a child's history into Main. The collapsed dock stays compact, with only pending/actionable notices above the composer.
- Keep current Main/View execution visible in a compact running rail at the bottom of the page surface; clicking it opens the owning Thread's history. Render user-facing streamed text and public reasoning summaries, not raw orchestration JSON, HTML or internal prompts. Keep readers' scroll position while they inspect older messages and provide a return-to-latest action.
- Keep the Chat UI brand mark static and compact: no decorative product-menu chevron beside the logo, keep the Space section close to the brand, and ship a vector favicon for the browser tab.
- Main Page must compose the actual child results using `<chat-view view-id="..."></chat-view>` slots, with visible semantic relationships. A directory of cards/links is not a complete result. Do not restore a competing host canvas or copy child HTML into Main.
- Architecture, process, sequence and dependency Views should be diagram-first SVG with labelled edges, compact controls and useful selection feedback. HTML is a runtime container, not a requirement to generate a conventional website. Charts should be primary for metrics tasks.
- Child results update their embedded slots independently. Local selection can link related Views through bounded entity events without launching agent work. After assigned children settle, Main gets one bounded integration pass based on their real summaries; that pass may only change Main Page and relationships.
- Main composes **all** retained Views as live, bare iframe embeds with automatic content height. The host must not inject card borders, title bars, "已就绪" status badges, collapse controls or open buttons. Main owns layout, styling, optional labels and folding; use accessible authored controls only when the task benefits, preserve mounted iframes while folded, and never force authored details open or overwrite the page's layout. Default to showing real results together; do not substitute a directory. Backfill missing live embeds without moving Main's content into a disclosure. Main can use CSS and `--chat-view-height` for a deliberate viewport; natural height is the default.
- Main and View agents share a **draw-to-explain default**, including requests labelled overview/workbench/page. Choose from the user's question (relationships, sequence, states, dependencies, comparison, quantities), not website templates or keywords. Main briefs state the representation and reason; each View checks that choice independently. Keep real forms/editors when the user needs to operate them, and short answers as text. Validate with outcome-only prompts whose expected representation is withheld from agents; SVG presence alone is not acceptance.
